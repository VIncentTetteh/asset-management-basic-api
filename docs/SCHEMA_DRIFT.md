# Schema drift: Flyway migrations vs JPA entities

Generated 2026-08-12 by diffing two PostgreSQL 16 databases:

- **flyway** - all 30 migrations applied via `flyway:migrate` (all reported success)
- **entity** - schema generated by Hibernate `ddl-auto=create` from the entity mappings

## Why this matters

`application-prod.yml` forces `ddl-auto=validate`, and `StartupSecurityValidator` refuses
to boot with a mutating value outside a dev profile. Hibernate validates the mapping
against the live schema at startup, so **the application cannot start against a
migration-built database** while these differences exist. It fails on the first one it
meets and reports only that one, which is why the full diff is recorded here.

The drift was invisible until now because nothing ever compared the two: the test
profile runs H2 with `create-drop` (schema generated *from* the entities), the CI
migration job applies migrations without starting Spring, and local development runs
with `SPRING_JPA_HIBERNATE_DDL_AUTO=update`, which lets Hibernate quietly reshape the
database instead of failing. `ValidatesAgainstFlywaySchemaTest` now closes that gap.

## Scale

| | Count |
|---|---|
| Columns the entities expect that migrations do not create | **184** |
| Columns whose type or length disagree | **83** |

| Tables affected | **49** |

## Each difference needs a decision, not a script

For every row below, one side is correct and the other is a bug, and which is which
cannot be inferred mechanically. `billing_payment` is the clearest example: the
migration creates `amount`, `description`, `payment_date`, `paystack_reference`, while
the entity expects `amount_minor`, `reference`, `paid_at` and eight more. That is not a
drifted column type, it is two different designs of the same table, and reconciling it
is a data-model decision with consequences for existing rows.

Auto-generating `ADD COLUMN` for all of these would produce a schema that validates and
still loses data on write.
